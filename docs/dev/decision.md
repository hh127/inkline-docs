# 技术选型

## 背景

VBA 版能跑，但有三个结构性痛点：

1. **依赖 VBA 会员/宏环境**：单位授权、宏安全策略、部分环境直接禁用；
2. **分发与安全**：xlsm 容易被杀软/邮件网关拦截，版本分发靠人工复制；
3. **单技术栈的天花板**：UI 只能用 UserForm/WebBrowser，难以做现代交互。

目标形态要同时满足：实时事件、Ribbon 功能区、任务窗格、单元格自定义函数、规范分发。

## 三条路线

| 路线 | 做法 | 结论 |
| --- | --- | --- |
| **A. 纯 JS 官方加载项重写** | 用 WPS 官方加载项（`wps` 宿主）重写全部能力 | ✅ **采用** |
| B. 双技术栈（JS 壳 + VBA 核） | JS 做 UI/事件，VBA 保留计算与批注 | ❌ 不成立 |
| C. 维持 xlam 增量优化 | 继续在 VBA/加载项化上打补丁 | ❌ 放弃 |

## 为什么 A 成立

关键验证结论（详见 `docs/WPS官方插件化改造方案-可行性评估.md`）：

| 能力 | 结论 |
| --- | --- |
| 实时事件拦截 | ✅ `wps.ApiEvent.AddApiEventListener` 可用，事件驱动而非轮询 |
| 审计快照 / 撤销重做 / 批注写回 | ✅ 可行 |
| Ribbon 功能区 / 任务窗格 | ✅ 加载项原生支持，体验优于 UserForm |
| 单元格自定义函数 | ✅ `wps.AddCustomFunction`（需官方加载项形态） |
| 离线可用 | ⚠️ 除 ECharts CDN 外均离线 |
| 无 VBA 依赖 | ✅ 免会员校验、无宏报毒、单技术栈 |

早期曾尝试"JS 宏编辑器 + 单元格函数"路线，实测证明**宏编辑器（`Application` 宿主）不支持单元格 UDF**，该路线已废弃；随后确认官方加载项形态可同时满足功能区、事件与单元格函数，因此改判为路线 A。

## 为什么 B 不成立

路线 B 的前提是"官方加载项事件能力不足，需要 VBA 兜底"。验证后发现 `SheetChange` 等事件在官方加载项中可用，且批注、撤销栈、UI 都可纯 JS 实现——保留 VBA 核只会带来双运行时同步、双份测试与分发复杂度，收益为负。

## 为什么 C 被放弃

xlam 方案无法摆脱 VBA 运行时与宏安全策略；每次分发仍是"发文件 + 教用户启用宏"，与目标（规范分发、无感升级）冲突。

## 迁移后的取舍（代价）

路线 A 不是无损迁移，以下能力**有意不做**：

| 能力 | 原因 | 替代 |
| --- | --- | --- |
| 表内悬浮按钮 | 加载项没必要在单元格上画按钮 | Ribbon + 侧边栏 |
| 快捷键体系 | 与宿主快捷键冲突风险 | Ribbon 按钮 |
| 大屏落盘 | 任务窗格内渲染更自然 | 任务窗格/侧边栏 |
| UserForm 模态窗体 | 平台无对应 API | HTML 任务窗格 + 编号多选提示 |

完整对照见[双实现能力矩阵](/dev/parity.html)。

## 代价与收益

| | VBA | WPS JS 加载项 |
| --- | --- | --- |
| 分发 | 发 xlsm，用户启用宏 | 静态目录 + `publish.xml`（或官方渠道） |
| 升级 | 逐台替换文件 | 换服务端目录，客户端重启 |
| 技术栈 | VBA + WebBrowser | 单一 JS |
| 测试 | 难自动化 | 19 套件 / 1034 断言可 Node 运行 |
| 平台风险 | 低（成熟） | 事件能力随 WPS 版本有差异 |

## 结论

**WPS 官方 JS 加载项是当前唯一同时满足"实时审计 + 现代 UI + 规范分发 + 可测"的形态**，因此成为主线；VBA 版作为 4.66 冻结基线保留，供仍以 Excel 为主的用户使用。
