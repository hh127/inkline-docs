# 表结构同步与轮询兜底

## 症状

这条踩坑有两次反复，按时间顺序看：

1. **不同步**：新增/删除/重命名工作表后，配置表「工作表名称」列不更新；
2. **更卡了**：加上同步逻辑后，用户反馈"加载项一启动就卡好一会儿"；
3. **还是卡**：继续优化事件后，真机反馈"改一个单元格就卡"。

## 根因

| 阶段 | 根因 |
| --- | --- |
| 不同步 | 依赖表结构事件，而部分 WPS 版本不触发（平台限制） |
| 更卡（第一次） | 每次 `SheetChange` 都枚举全部表名（O(n) 次 COM），改一格也扫全表 |
| 还是卡（第二次） | 真正卡源是两个叠加：**O(10000) 逐格 COM 扫描** + **未关闭屏幕刷新**；另外删除表后立即同步会读到"删除未完成"的中间状态 |

## 方案

### 1. 同步策略（三条路径 + 兜底）

- 原生事件（`WorkbookNewSheet` / `SheetBeforeDelete` / `SheetActivate`）能触发就立即同步；
- `SheetChange` 时只读 `Sheets.Count`（1 COM）做数量快道；
- 用内存注册表比对表名（0 COM）做名字快道，抓原地改名；
- 轮询兜底：每 5 秒一次 Count，每 2 次做一次全名枚举（约 10 秒）；
- 删除后最多 10 次 × 50ms 重试，等宿主真正删完再全量同步。

### 2. 性能修正

| 修正 | 做法 |
| --- | --- |
| 解耦事件与枚举 | 事件回调只做便宜判断，昂贵枚举交给兜底 |
| 批量读替代逐格 | `readMatrix`/`writeMatrixRow` 一次拿整块，禁止逐格 COM |
| 屏幕刷新 | 大区域操作前关 `screenUpdating`，`finally` 恢复 |
| 事件防重入 | `_handlingChange` 守卫，避免自身写入再次触发 |

### 3. 删除等待

删除表是异步动作：`SheetBeforeDelete` 触发时表还在，直接同步会拿到旧状态。所以用短重试窗口等待宿主完成。

## 验证

- 新增 / 删除 / 改名三种操作：最迟约 10 秒内配置表正确；
- 改单元格时无全表枚举（用日志或性能体感验证）；
- 删除后不出现"幽灵表"（已删表仍留在配置表）。

## 你也遇到了？

- ☐ 等待 10 秒是否恢复（恢复 = 事件没来，走兜底）
- ☐ 是否只在"频繁改单元格"时卡（检查是否有逐格 COM）
- ☐ 删除表后配置表是否残留（检查删除重试窗口）
